# REA 점검 및 수정 결과 — 2026-10-21

로컬 SCM 실행 JAR를 REA의 `capture_browser_scenario`로 조작하고 HTTP 응답·DOM을 관찰했다. 재현한 정렬 오류와 거래처 검색 누락, 별도의 서버 통합 테스트로 재현한 비밀번호 오류를 수정했다. 기존 작업 내용은 보존했으며 커밋은 생성하지 않았다.

## 확인한 문제와 수정

| 문제 | 수정 전 | 수정 후 | 근거 |
| --- | --- | --- | --- |
| 잘못된 정렬 필드 | `sort=missing`을 보낸 품목·거래처·재고·수주 조회가 HTTP 500을 반환 | DB 조회 전에 도메인별 허용 필드를 검사해 `400 INVALID_INPUT` 반환 | REA S1/S2, `SortValidationIntegrationTest` 50건 |
| 과거 주문 거래처 검색 누락 | 공급사를 고객사로, 고객사를 공급사로 바꾸면 주문 행은 남지만 검색 드롭다운에서 해당 거래처가 사라짐. 비활성 공급사도 발주 검색에서 제외됨 | 현재 적합한 유형 또는 해당 주문 이력이 있는 거래처를 검색 옵션에 포함. 신규 주문 작성은 기존의 유형·활성 조건 유지 | REA P1/P2·O1/O2, `OrderPartnerFilterIntegrationTest` 6건 |
| 한글·이모지 비밀번호 변경 오류 | 문자 수 제한을 통과해도 UTF-8로 72바이트를 넘으면 BCrypt 해시 과정에서 예외가 나 HTTP 500 반환 | 해시 전에 바이트 길이를 검사해 `400 INVALID_INPUT` 반환. 저장된 비밀번호는 유지 | `PasswordBoundaryIntegrationTest` 8건; REA 브라우저 증거와 구분 |

정렬 검증은 목록 화면과 API가 공유하는 서비스에 적용했다. 일반 목록의 존재하지 않는 필드·중첩 경로·다중 정렬 내 잘못된 조건을 거부하고, 정상 다중 정렬은 유지한다. 재고는 조회 기준인 품목 필드를 사용하며 공지 목록은 기존의 고정 정렬을 유지한다.

비밀번호 테스트는 한글 25자, 이모지 19개, 한글 24자+ASCII 1자를 거부하고, 한글 24자·이모지 18개(각 72바이트) 및 ASCII 64자의 변경 후 실제 로그인 성공까지 확인한다.
