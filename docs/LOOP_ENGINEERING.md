# SCM 워크북 루프 엔지니어링 가이드

> [HTML 학습 목차](../index.html) · [프로젝트 README](../README.md) · [문서 지도](./INDEX.md) · [취업 포트폴리오 가이드](./PORTFOLIO_GUIDE.md)

이 문서는 SCM 프로젝트를 한 번 완성하고 끝내는 코드가 아니라, **직접 구현하고 설명하면서 취업 역량을 증명하는 워크북**으로 계속 개선하기 위한 운영 기준이다.

## 1. 최상위 목표

이 저장소의 모든 변경은 다음 두 목표에 기여해야 한다.

1. **취업용 워크북**: Java/Spring 기반 SI·백엔드 직무에서 요구하는 요구사항 분석, 계층 설계, 상태 전이, 트랜잭션, 보안, 테스트, 장애 대응 능력을 직접 연습하고 증명한다.
2. **쉬운 학습 탐색**: 루트 `index.html`에서 학습 순서, 40개 모듈, 설계 문서, 구현 코드, 테스트 증거와 면접 자료로 바로 이동할 수 있게 한다.

기능 수만 늘리는 것은 목표가 아니다. 새 기능은 반드시 “왜 이렇게 설계했는가”, “실패하면 어떻게 되는가”, “테스트로 무엇을 증명했는가”까지 설명할 수 있어야 완료다.

## 2. 기준 문서 우선순위

문서와 구현이 다를 때는 아래 순서로 판단한다.

1. 현재 실행되는 테스트가 증명하는 동작
2. `practice/DESIGN_DECISIONS.md`와 `docs/STATE_MACHINE.md`
3. 현재 `src/` 구현
4. `docs/API_SPEC.md`, `docs/ERD.md`
5. 원본 요구사항 `scm_system_PRD_TRD.md`

원본 PRD/TRD는 출발점이므로 조용히 고치지 않는다. 구현과 달라진 결정은 `DESIGN_DECISIONS.md` 또는 `TROUBLESHOOTING.md`에 이유를 남긴다.

## 3. 하나의 표준 루프

모든 학습·문서·기능 개선은 아래 8단계를 한 사이클로 수행한다.

| 단계 | 질문 | 필수 산출물 |
|---|---|---|
| 1. 목표 | 취업 역량 또는 사용자 가치가 무엇인가? | 한 문장 목표 |
| 2. 기준선 | 지금 구현과 테스트는 어디까지 동작하는가? | 관련 코드·문서·테스트 목록 |
| 3. 계약 | 입력, 출력, 권한, 상태, 실패 조건은 무엇인가? | 규칙표 또는 API/상태 계약 |
| 4. 실패 증거 | 잘못된 구현을 어떤 테스트가 잡는가? | 먼저 실패하는 테스트 또는 재현 절차 |
| 5. 최소 변경 | 계약을 만족하는 가장 작은 변경은 무엇인가? | 코드·문서 변경 |
| 6. 검증 | 관련 테스트와 전체 회귀가 통과하는가? | 실행 명령과 결과 |
| 7. 설명 | 면접에서 1분 안에 선택 이유를 말할 수 있는가? | 학습 노트·트레이드오프 |
| 8. 정리 | 문서, HTML 목차, 이력이 현재 구현과 같은가? | 링크·문서 동기화, 작은 커밋 |

루프 중 문제가 발견되면 5단계에서 임시로 숨기지 말고 2단계로 돌아가 기준선을 다시 잡는다.

## 4. 네 가지 반복 트랙

### 4.1 학습 루프

```text
문제 읽기 → 답을 보지 않고 예측 → workspace에서 구현
→ 정상 1건·실패 3건 작성 → 참조 코드와 비교
→ 자신의 말로 설명 → 다음 날 재현
```

```bash
./gradlew practiceInit       # 최초 1회
./gradlew practiceStatus
./gradlew practiceCheck
./gradlew test
```

완료 기준은 빈칸 개수가 0인 것만이 아니다. 트랜잭션 경계, 권한 위치, 금지 상태 전이와 동시성 위험을 설명할 수 있어야 한다.

### 4.2 기능 구현 루프

```text
요구사항 → 상태/권한 표 → 실패 테스트 → Domain/Service
→ Controller/View → 통합 테스트 → 문서와 HTML 링크 갱신
```

변경 중에는 관련 테스트만 실행하고, 종료 전에 전체 테스트와 실행 가능한 JAR를 검증한다.

```bash
./gradlew test --tests '*PurchaseOrderServiceTest'
./gradlew test
./gradlew bootJar
./gradlew portfolioCheck
```

### 4.3 문서 정리 루프

1. 실제 코드의 Controller 매핑, DTO, enum, DB 컬럼을 읽는다.
2. `API_SPEC`, `ERD`, `STATE_MACHINE`과 차이를 찾는다.
3. 구현이 맞으면 문서를, 계약이 맞으면 테스트와 구현을 수정한다.
4. `docs/INDEX.md`와 `index.html`의 링크를 확인한다.
5. 문서에 “구현됨/확장 과제”를 명확히 표시한다.

### 4.4 취업 포트폴리오 루프

```text
기능 선택 → 3분 데모 → 설계 질문 5개 답변
→ 장애/실패 사례 설명 → 이력서 한 줄 작성 → 모의 면접 피드백
```

기능 하나마다 다음 증거를 남긴다.

- 요구사항 또는 업무 규칙
- 핵심 코드 위치
- 자동 테스트
- 트러블슈팅 기록
- 화면 또는 실행 시나리오
- 이력서·면접 설명

## 5. 검증 단계

| 단계 | 실행 시점 | 검증 |
|---|---|---|
| L1 빠른 검사 | 파일 저장 후 | 대상 단위 테스트 |
| L2 모듈 검사 | 한 규칙 완료 후 | Service + Repository/MockMvc 테스트 |
| L3 전체 검사 | 루프 종료 전 | `./gradlew test` |
| L4 패키징 | 커밋 전 | `./gradlew bootJar` |
| L5 실행 검사 | 기능 묶음 완료 후 | H2 또는 Docker로 핵심 사용자 흐름 |
| L6 포트폴리오 검사 | 주 1회 | 3분 데모 + 면접 질문 답변 |

테스트를 통과하지 못한 변경은 “거의 완료”가 아니라 진행 중이다. 현재 환경 제약으로 실행하지 못했다면 그 이유와 마지막 성공 증거의 시점을 함께 기록한다.

## 7. Definition of Done

하나의 루프는 아래 항목을 모두 만족해야 종료한다.

- [ ] 목표가 취업 역량 또는 학습 편의와 연결된다.
- [ ] 정상 경로와 실패 조건이 문서에 있다.
- [ ] 권한·상태·트랜잭션 경계가 코드와 테스트에 있다.
- [ ] 대상 테스트와 전체 회귀 테스트가 통과한다.
- [ ] H2 전용 동작인지 MySQL에서도 보장되는지 표시했다.
- [ ] `README`, `docs`, `practice`, `index.html` 중 영향받는 문서를 갱신했다.
- [ ] 면접에서 선택 이유와 대안을 설명할 수 있다.
- [ ] 변경 범위가 작은 커밋 단위로 분리됐다.

```text

1) 먼저 현재 코드·문서·테스트의 기준선을 확인한다.
```

“완벽한 프로그램”은 결함이 영원히 없는 상태가 아니라, 새 결함과 요구사항을 위 루프로 빠르게 발견하고 안전하게 개선할 수 있는 상태로 정의한다.

## 11. 적용 기록 — MySQL·동시성·재고 수직 슬라이스 (2026-07-18)

### Loop 2 — MySQL 스키마 계약

- 목표: 운영 MySQL이 Hibernate의 암묵적 DDL에 의존하지 않게 한다.
- 실패 조건: `ddl-auto=update`, 변경 이력 부재, H2만 통과하는 스키마.
- 변경: Flyway 기준 마이그레이션, `ddl-auto=validate`, MySQL 8.4 LTS CI 서비스와 `mysqlSchemaTest`.
- 검증: 마이그레이션 전체 SQL을 H2 MySQL 모드에서 실행했다. 실제 MySQL 적용과 JPA 검증은 CI 전용 테스트가 수행한다.
- 1분 답변: “Flyway가 변경 이력을, Hibernate validate가 엔티티와 실제 스키마의 현재 일치를 검증하도록 책임을 분리했습니다.”

### Loop 3 — 발주번호와 최초 재고 경합

- 목표: 같은 날짜의 동시 발주와 같은 품목의 동시 최초 입고에서 데이터 정합성을 지킨다.
- 실패 조건: 중복 발주번호, 삭제된 번호 때문에 같은 번호 반복, 재고 두 행 또는 수량 유실.
- 변경: 당일 최대 번호 기반 채번, 9999 상한, UNIQUE 충돌 독립 트랜잭션 재시도, 품목 ID 순서 잠금.
- 검증: 두 스레드 발주 생성과 두 스레드 최초 입고 통합 테스트를 실행했다. UNIQUE 충돌 후 재채번과 재고 한 행·합산 수량을 확인했다.
- 1분 답변: “애플리케이션 계산만 신뢰하지 않고 UNIQUE 제약을 최종 방어선으로 두고, 실패한 영속성 컨텍스트를 재사용하지 않도록 저장 시도를 독립 트랜잭션으로 분리했습니다.”

### Loop 4 — 재고 조회 수직 슬라이스

- 목표: 입고 결과를 사용자가 화면과 API에서 확인하고 안전재고 부족을 바로 찾게 한다.
- 정상 조건: 운영 품목 전체, 현재고·안전재고·부족수량·상태, 검색·필터·요약.
- 실패 조건: 입고 이력이 없는 품목 누락, 단종 품목 포함, 미로그인 조회, 화면/API 계산 불일치.
